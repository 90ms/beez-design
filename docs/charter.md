# BEEZ Design System Charter

## 1. 문서의 목적

이 문서는 BEEZ Design System의 존재 이유와 범위, 운영 원칙을 정의한다.

BEEZ에서 새로운 토큰, 컴포넌트, 도구 또는 플랫폼 지원을 제안할 때는 이 문서를 공통 판단 기준으로 사용한다. 구현 방식이 바뀌더라도 이 문서에 정의된 목적과 원칙은 일관되게 유지한다.

## 2. 비전

BEEZ는 여러 제품이 동일한 디자인 언어를 공유하면서도 각 제품의 목적과 맥락에 맞게 확장할 수 있도록 돕는 멀티플랫폼 디자인 시스템이다.

디자인 결정을 재사용 가능한 토큰, 컴포넌트, 패턴과 문서로 표현하고, 디자인과 코드, 사람과 AI 에이전트가 같은 기준을 바라보게 한다.

## 3. 목표

BEEZ는 다음을 목표로 한다.

- 새로운 프로젝트에서 반복되는 디자인 및 UI 구현 결정을 줄인다.
- Compose Multiplatform 프로젝트에 일관된 사용자 경험을 제공한다.
- 디자인 의도를 플랫폼에 종속되지 않는 명세로 관리한다.
- 접근성, 상태, 테마 및 반응형 동작을 개별 제품이 매번 다시 설계하지 않게 한다.
- 토큰과 컴포넌트의 사용법뿐 아니라 사용 이유와 제약도 함께 제공한다.
- 라이브러리, 문서, 쇼케이스 및 AI 에이전트가 동일한 원본 명세를 사용하게 한다.
- 핵심 라이브러리를 Material 구현과 버전에 종속시키지 않는다.
- 변경을 예측 가능하게 배포하고 기존 사용자의 마이그레이션을 지원한다.

## 4. 주요 사용자

### 제품 개발자

검증된 토큰과 컴포넌트를 dependency로 추가하여 제품 UI를 빠르고 일관되게 구현한다.

### 디자이너

코드와 연결된 토큰, 컴포넌트 및 패턴을 사용해 구현 가능한 디자인을 만든다.

### 디자인 시스템 기여자

공통 명세와 완료 기준에 따라 토큰, 컴포넌트, 문서 및 도구를 개선한다.

### AI 에이전트

기계가 읽을 수 있는 명세와 작업 절차를 바탕으로 BEEZ에 맞는 코드를 작성하고 검증한다.

## 5. 핵심 산출물

BEEZ는 다음 산출물을 제공한다.

- 색상, 타이포그래피, 크기, 간격, 모서리, 고도 및 모션 등의 디자인 토큰
- 테마와 토큰 접근 API를 포함하는 Compose Multiplatform 기반 요소
- 재사용 가능한 UI 컴포넌트
- 반복되는 제품 문제를 해결하는 UI 패턴과 사용 지침
- 실제 컴포넌트와 상태를 확인할 수 있는 카탈로그
- 디자인 원칙, 명세, API 및 마이그레이션을 설명하는 문서 사이트
- 기여와 구현을 돕는 AI Agent Skill 및 기계 판독용 문서
- 버전이 부여된 라이브러리 배포물과 변경 이력

## 6. 설계 원칙

### 명세가 먼저다

토큰과 컴포넌트는 구현 전에 이름, 목적, 사용 조건, 상태 및 제약을 정의한다. 구현 코드나 Figma 파일 하나만을 유일한 원본으로 간주하지 않는다.

### 의미를 값보다 우선한다

제품 코드는 원시 색상이나 임의의 크기보다 역할과 의도를 나타내는 semantic token을 우선 사용한다.

### 일관성과 확장성의 균형을 유지한다

일관된 기본값을 제공하되, 실제 제품 요구를 해결할 수 있는 명시적 확장 지점을 제공한다. 제한을 우회하기 위한 무분별한 옵션 추가는 피한다.

### 기본 정체성과 브랜드 확장을 함께 제공한다

BEEZ는 별도 설정 없이 사용할 수 있는 기본 테마와 시각적 정체성을 제공한다. 제품별 브랜드는 원시 값을 직접 수정하거나 컴포넌트를 복제하는 대신 semantic token을 교체하여 표현한다.

### 접근성은 완료 조건이다

명도 대비, 터치 영역, 키보드 조작, 스크린리더, 동적 글꼴 크기 및 모션 감소 설정은 부가 기능이 아니라 기본 요구사항으로 다룬다.

### 공통 동작과 플랫폼 관습을 함께 존중한다

가능한 동작과 API는 `commonMain`에서 일관되게 제공한다. 플랫폼 관습이나 시스템 기능이 더 적절한 경우에는 차이를 숨기지 않고 명세와 문서에 기록한다.

### 공개 API는 작고 예측 가능하게 유지한다

구현 세부사항은 숨기고, 이름과 기본값만으로 의도를 이해할 수 있는 API를 제공한다. 공개 API 변경은 호환성과 마이그레이션 비용을 검토한다.

### Material과 독립적인 핵심을 유지한다

BEEZ 핵심 컴포넌트는 Compose Runtime, UI 및 Foundation을 구현 기반으로 사용하며 Material 3에 의존하지 않는다. Material 연동이 필요하면 핵심 모듈과 분리된 선택형 adapter로 제공한다.

### 문서와 구현은 함께 변경한다

토큰이나 컴포넌트의 변경은 관련 명세, 카탈로그, 테스트 및 변경 이력과 함께 반영한다.

### 실제 필요에서 성장한다

가능성을 예상해 컴포넌트를 대량으로 만들지 않는다. 둘 이상의 제품에서 반복되거나 공통화 가치가 확인된 문제부터 시스템에 포함한다.

## 7. 초기 범위

초기 버전은 디자인 시스템을 실제 프로젝트에서 검증할 수 있는 최소 수직 단면을 만드는 데 집중한다.

### Foundations

- Color
- Typography
- Dimension 및 Spacing
- Radius
- Elevation
- Motion
- Light 및 Dark theme
- BEEZ 기본 테마와 semantic token 기반 브랜드 확장
- UI state
- 접근성 기준

### Components

초기 컴포넌트는 토큰부터 명세, 구현, 테스트, 카탈로그 및 문서까지 전체 흐름을 검증할 수 있는 작은 집합으로 제한한다.

- Text
- Icon
- Action Button
- Checkbox
- Text Field
- Surface 또는 Card

컴포넌트 목록은 구현 과정에서 검토할 수 있으며, 이 목록 자체가 구현 순서를 의미하지는 않는다.

### Platforms

초기 지원 우선순위는 다음과 같다.

| 등급 | 플랫폼 | 의미 |
| --- | --- | --- |
| Tier 1 | Android | 주요 개발 및 품질 검증 대상 |
| Tier 2 | iOS, Desktop | 공통 API와 주요 동작 지원 대상 |
| Experimental | Web/Wasm | 카탈로그와 배포 가능성을 검증하는 실험 대상 |

플랫폼 등급은 테스트 환경과 실제 사용 경험이 확보되면 변경할 수 있다.

## 8. 초기 비범위

다음 항목은 중요하지만 초기 버전의 필수 범위에는 포함하지 않는다.

- 모든 Material 컴포넌트의 대체
- 특정 제품 도메인에만 필요한 비즈니스 컴포넌트
- 완성된 화면이나 기능 단위 템플릿의 대규모 제공
- 모든 플랫폼의 픽셀 단위 동일성
- SwiftUI, UIKit, Android View, React 또는 DOM용 별도 컴포넌트 구현
- Figma와 코드의 완전 자동 양방향 동기화
- 전용 CLI, IDE 플러그인 또는 MCP 서버
- 브랜드별 컴포넌트 포크와 복잡한 화이트라벨 관리 기능
- 안정화되지 않은 API에 대한 장기 호환성 보장

비범위 항목도 실제 필요와 유지 가능성이 확인되면 별도 의사결정 기록을 거쳐 포함할 수 있다.

## 9. 원본과 파생물

BEEZ는 디자인 결정을 사람이 이해할 수 있고 기계가 처리할 수 있는 형태로 관리한다.

### 원본

- 프로젝트 헌장과 디자인 원칙
- 구조화된 디자인 토큰
- 컴포넌트 및 패턴 명세
- Architecture Decision Record

### 파생물

- Kotlin 및 플랫폼별 토큰 코드
- Compose Multiplatform 구현
- 카탈로그와 문서 사이트
- API 레퍼런스와 코드 예제
- AI Agent Skill의 참조 자료

파생물 사이에 차이가 발생하면 원본 명세를 기준으로 해결한다. 원본 명세가 실제 요구를 잘못 표현한 경우에는 명세를 먼저 수정하고 파생물을 갱신한다.

## 10. 시스템 편입 기준

새로운 항목은 다음 질문에 답할 수 있을 때 BEEZ에 포함한다.

- 둘 이상의 화면이나 제품에서 재사용할 가능성이 있는가?
- 사용자 경험 또는 브랜드 일관성에 의미 있는 영향을 주는가?
- 기존 토큰, 컴포넌트 또는 패턴으로 해결할 수 없는가?
- 명확한 목적과 사용하지 말아야 할 상황을 설명할 수 있는가?
- 접근성과 플랫폼별 동작을 정의할 수 있는가?
- 테스트와 문서를 지속해서 유지할 수 있는가?

조건을 만족하지 않는 구현은 먼저 제품 로컬 컴포넌트로 유지하고, 반복되는 요구가 확인되면 BEEZ로 승격한다.

## 11. 변경과 의사결정

- 중요한 설계 및 기술 결정은 Architecture Decision Record로 남긴다.
- 공개 API와 토큰 이름은 Semantic Versioning 관점에서 관리한다.
- 호환성을 깨는 변경에는 변경 이유와 마이그레이션 방법을 제공한다.
- 더 이상 권장하지 않는 API는 가능한 경우 즉시 제거하지 않고 deprecated 상태를 거친다.
- 플랫폼별 구현 상태와 알려진 차이를 공개적으로 기록한다.
- 자동 생성된 결과물은 직접 수정하지 않는다.

## 12. 성공 기준

BEEZ의 성공은 컴포넌트 개수보다 실제 재사용성과 신뢰도로 판단한다.

- 새 프로젝트가 BEEZ를 dependency로 추가해 테마와 기본 컴포넌트를 사용할 수 있다.
- 동일한 명세에서 둘 이상의 플랫폼 구현을 제공할 수 있다.
- 임의의 색상, 간격 및 텍스트 스타일 사용이 제품 코드에서 감소한다.
- 컴포넌트의 상태, 접근성 및 사용 지침을 카탈로그와 문서에서 확인할 수 있다.
- 변경 사항과 마이그레이션 영향을 배포 전에 확인할 수 있다.
- 사람과 AI 에이전트가 동일한 규칙을 따라 유사한 품질의 결과를 만든다.
- 실제 제품에서 발견된 문제와 개선점이 다시 시스템에 반영된다.

## 13. 열린 질문

다음 항목은 후속 문서와 Architecture Decision Record에서 결정한다.

- Kotlin 이외 token 생성 대상과 도구 확장 범위 (DTCG 형식과 Kotlin 생성 경계는 token taxonomy 및 ADR-0012에서 결정)
- 아이콘 제공 및 배포 방식
- 카탈로그 및 문서 사이트의 후속 문서 사이트 기술 스택 (Showcase는 ADR-0011에 따라 Compose Multiplatform Catalog로 운영)
- 스크린샷 테스트와 접근성 테스트 전략
- 릴리스 저장소와 배포 정책
- Figma 연동 시점과 동기화 방향
- AI Agent Skill 및 향후 문서 MCP의 제공 범위

## 14. 헌장 변경

이 헌장은 구현 세부사항이 아니라 BEEZ의 장기적인 방향을 정의한다. 목표, 주요 사용자, 범위 또는 핵심 원칙을 변경할 때는 변경 이유와 영향을 기록하고 검토한다.
